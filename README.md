## 3. State อยู่ที่ไหน ทำไม

### (ก) ทำไมคำค้นและธาตุอยู่ใน URL ไม่ใช่ `useState`

- **แชร์ลิงก์ได้ (Shareable URL):** ผู้ใช้สามารถ copy ลิงก์ (เช่น `?q=saur&type=grass`) ส่งต่อหรือเปิดในแท็บใหม่แล้วได้ผลลัพธ์ตรงกันทันที
- **รองรับประวัติเบราว์เซอร์ (Browser Navigation):** สามารถกด Back / Forward ได้ และการใช้ `{ replace: Boolean(q) }` ช่วยให้กด Back ครั้งเดียวเพื่อออกจากการค้นหาได้ทันที ไม่ถอยทีละตัวอักษร
- **รีเฟรชแล้วข้อมูลไม่หาย:** เมื่อกด Refresh (F5) หรือ Bookmark ไว้ ข้อมูลการค้นหายังคงอยู่ตาม URL
- **Single Source of Truth:** ให้ URL เป็นแหล่งข้อมูลความจริงจุดเดียว ช่วยลดความซ้ำซ้อนและป้องกันปัญหา State ไม่ตรงกับหน้าจอ

### (ข) ทำไมทีมหยุดที่ Context

ไล่ตาม Decision Framework:
1. **`useState` ในหน้าเดียว (ไม่พอ):** ข้อมูลทีมต้องใช้งานข้ามหลายหน้าพร้อมกัน (`Nav`, `Home`, `PokemonList`, `PokemonDetail`, `Team`)
2. **Lift State Up (ไม่เหมาะ):** หากยก state ไปไว้ที่ Root จะเกิดปัญหา **Prop Drilling** ที่ต้องส่ง props ผ่าน Component กลางหลายระดับโดยไม่จำเป็น
3. **Context (`TeamContext` — เหมาะสมที่สุด):** สามารถครอบ Provider ที่ระดับบนสุดแล้วเรียกใช้ผ่าน `useTeam()` ได้โดยตรงจากทุกที่ อีกทั้งข้อมูลทีมมีขนาดเล็ก (สูงสุด 6 ตัว) และไม่ได้อัปเดตถี่ จึงไม่มีปัญหาเรื่องประสิทธิภาพ
4. **Redux / Zustand (เกินจำเป็น):** สถาปัตยกรรมของแอปไม่ได้ซับซ้อน การใช้ Context + Custom Hook และ `localStorage` เพียงพอแล้วโดยไม่ต้องเพิ่ม Dependency ภายนอก

### (ค) `memo` / `useMemo` / `useCallback` — หรือเหตุผลที่ไม่ใช้

**ไม่ได้ใช้เลย** เนื่องจาก:
- **ชุดข้อมูลมีขนาดเล็ก:** โปเกมอนมีเพียง 151 ตัว และทีมมีไม่เกิน 6 ตัว การคำนวณอย่าง `.filter()`, `.map()`, `has()` ทำงานในระดับเสี้ยววินาที (Sub-millisecond)
- **ไม่มีการคำนวณที่ซับซ้อน:** มีเพียงการแปลงหน่วย ม./กก. และจัดฟอร์แมตข้อความธรรมดา
- **หลีกเลี่ยง Premature Optimization:** การใช้ Hook เหล่านี้มี Overhead ในการจองหน่วยความจำและเปรียบเทียบ Dependencies หากไม่มีปัญหาคอขวดจริงจะทำให้โค้ดซับซ้อนโดยไม่จำเป็น
- **React 19 ทำงานได้เร็วอยู่แล้ว:** ระบบ Reconciliation จัดการ Re-render ของแอปขนาดนี้ได้สบาย การเขียนโค้ดที่กระชับและอ่านง่ายจึงเหมาะสมที่สุด
